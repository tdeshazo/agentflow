# AgentFlow v1alpha4 work-item authoring contract

`agentflow.dev/v1alpha4` preserves v1alpha3 typed handoffs and adds typed,
runtime-owned work-item completion. Use it when a workflow must advance a
finite set of criteria without making a Markdown file, actor message, or
procedural loop the source of truth.

The structural authority is the checked-in
[machine-readable executable schema](../../schema/v1alpha4.schema.json),
generated by `workflow.GeneratedSchema` from the strict v1alpha4 decoder.
`agentflow validate` rejects missing, duplicate, or unbounded work-item
advancement before an actor runs.

## Typed work items

Declare stable IDs and human-readable descriptions under `spec.criteria.items`.
Every item must have exactly one advancing phase. A phase names one item with
`workItem` and sets `advanceWorkItem: true`; after its deterministic validation
passes, the runtime writes durable completion for that exact item. A completed
phase marker without matching work-item state is rejected on reuse.

```yaml
criteria:
  items:
    - id: add-api
      description: Add the API capability.
phases:
  - id: implement-api
    kind: implementation
    actor: implementer
    prompt: Implement the API capability.
    validation: quality
    workItem: add-api
    advanceWorkItem: true
```

The actor cannot advance an item. The runtime requires the item to be pending,
runs the declared deterministic validation, records only that item as
completed, checkpoints the accepted workspace, and then writes the phase
marker. Completion requires every declared work item to have durable state.

## Bounded collection expansion

Use `forEach` for a fixed collection with identical execution authority. It is
expanded before execution into ordinary dependency nodes with IDs
`<phase-id>--<work-item-id>`. `maxItems` must exactly equal the declared
`workItems` count, so expansion is finite and reviewable. A collection phase
must set `advanceWorkItem: true` and cannot emit a shared artifact.

```yaml
phases:
  - id: implement-items
    kind: implementation
    actor: implementer
    prompt: Complete only the assigned work item.
    validation: quality
    advanceWorkItem: true
    forEach:
      workItems: [add-api, add-tests]
      maxItems: 2
```

Each generated actor receives the assigned item ID and description in its
runtime prompt. Dependencies on a collection fan in on all of its generated
nodes. With `execution.maxParallel` enabled, generated nodes may run
concurrently when their enforced `writes` scopes resolve to disjoint paths;
for example, `items/{{ phase.id }}/**` gives each expanded phase a distinct
directory. A shared Markdown adapter is runtime-owned workspace state and
therefore serializes those transitions. This is static bounded expansion, not
a dynamic loop.

## Markdown checklist adapter

`criteria.markdownChecklist` is optional presentation output. It maps each
work-item ID to exactly one existing checklist label. The runtime verifies that
the checklist initially mirrors durable state, blocks actors from editing it,
and changes only the completed item after validation. Changing the checklist
does not advance work; deleting the adapter does not erase the durable state.

```yaml
criteria:
  items:
    - {id: add-api, description: Add the API capability.}
  markdownChecklist:
    path: progress.md
    items: {add-api: Add the API capability.}
```

Include the adapter path in `workspace.allowWrites` because the runtime
checkpoints its deterministic presentation update. The expanded plan exposes
the runtime-owned criteria, adapter, generated phases, and exact-target
acceptance transitions.
